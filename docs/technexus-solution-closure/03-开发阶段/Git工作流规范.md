# Git工作流规范

文档编号：`DEV-GIT-001`  
版本：`v0.1`  
状态：`评审中`  
仓库：`G:\project\TechNexus`  
工作流模式：Trunk-based + 短生命周期分支  
维护人：TechNexus 技术负责人

## 1. 仓库与所有权

| 范围 | 所有者 | 强制评审 |
|---|---|---|
| 领域与 server | 后端负责人 | 技术负责人；安全/DB 视风险加入 |
| web/admin | 前端负责人 | 前端负责人；安全评审认证变化 |
| migration | 数据库所有者 | DBA/技术负责人 |
| 安全与发布配置 | 安全/运维 | 安全负责人+发布负责人 |
| 受控文档 | 对应阶段负责人 | 阶段专家 |

## 2. 分支模型

`main` 始终可构建；使用 `codex/<id>-<slug>`、`feature/<id>-<slug>`、`fix/<id>-<slug>` 和 `hotfix/<id>-<slug>`。从 `main` 创建并合回 `main`，目标生命周期不超过 3 个工作日；合并后删除。发布用不可变 Tag，不维护长期 release 分支。

## 3. Commit规范

格式：`<type>(<scope>): <summary> [<work-item>]`，类型为 feat/fix/refactor/test/docs/build/chore。单提交单逻辑、可回滚；禁止密钥、`.env`、构建输出、依赖目录和无关格式化。

## 4. Pull/Merge Request

必须包含目的、需求/设计编号、文件与迁移范围、风险、验证命令/结果、配置变化、回滚方法、UI 截图（适用）和未完成项。大变更拆分评审，不允许以“后续再看”隐藏红线。

## 5. 审核与批准

| 风险 | 批准数 | 强制专家 | 自动检查 | 自合并 |
|---|---:|---|---|---|
| 低 | 1 | 代码所有者 | build/test/lint | 否 |
| 中 | 1 | 代码所有者 | +契约/SCA | 否 |
| 高 | 2 | 安全/DB/架构按范围 | 全部门禁 | 否 |
| 紧急 | 2 | 技术+业务风险接受人 | 可延期非红线检查 | 否 |

单人 Alpha 无法提供物理双人批准时，必须保留独立专家视角记录和用户显式风险接受，不能伪造批准人。

## 6. 分支保护

正式托管后禁止强推和删除 `main`，禁止直接提交；要求 clean verify、双前端 build、契约、SCA 和代码评审状态。管理员绕过必须留审计，密钥扫描阻断。

## 7. 合并策略

功能分支默认 Squash；迁移、可独立回滚的安全修复可保留独立提交。合并提交需带工作项；合并后用构建 ID 和制品 digest 追溯。

## 8. 版本与Tag

遵循 SemVer：Alpha 使用 `v0.y.z-alpha.n`，稳定发布 `vX.Y.Z`。Tag 只指向通过发布门禁的提交，禁止覆盖；制品记录 commit SHA、构建 ID、依赖锁文件 digest。

## 9. 发布与Hotfix

从已通过门禁的主干提交打 Tag；Hotfix 从生产 Tag 创建，修复后执行风险相关测试并合回主干，24 小时内补齐完整评审。

## 10. Revert与恢复

代码缺陷优先 revert；可关闭功能先关闭 Flag；数据库使用前向修复迁移，不回写已执行 migration。回滚后验证健康、核心路径和数据一致性，并建立根因记录。

## 11. 冲突处理

变更作者解决冲突；涉及迁移、契约或权限的冲突必须由对应专家重新评审，并重跑全量门禁，不接受仅凭可编译合并。

## 12. 追溯与审计

`需求 → 分支 → Commit → PR → 构建 → 制品 → Tag → 发布`。需求和设计保留期不少于产品生命周期；发布/安全/审计证据按合规要求保存。

## 13. 紧急例外

当前无已批准例外。现有工作区尚未提交，登记 `DEV-ISSUE-009`；只可在阶段评审通过并获得用户确认后建立基线提交，不以未提交状态进入测试阶段。
